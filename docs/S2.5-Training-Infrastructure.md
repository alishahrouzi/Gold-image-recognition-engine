# S2.5 — Training Infrastructure

## Scope

S2.5 provides reusable training infrastructure for the visual retrieval model.
It owns:

- Training loop
- Validation loop
- Optimizer construction
- Learning-rate scheduler
- Checkpointing and resume
- Structured training logging
- Early stopping
- Reproducible seed/RNG state handling

Metric-learning loss definitions and retrieval-specific semantics remain outside
this layer and are injected through the trainer step function. This preserves
the architecture boundary between training infrastructure and Sprint 3 metric
learning.

## Architecture

```text
TrainingConfig
      |
      +---- Seed / RNG
      |
      +---- Optimizer ---- Scheduler
      |
      +---- EarlyStopping
      |
      +---- CheckpointManager
      |
      +---- TrainingLogger
      |
      v
    Trainer
      |
      +---- run_training_epoch
      |          |
      |          +---- model.train()
      |          +---- forward/loss step
      |          +---- backward()
      |          +---- optimizer.step()
      |
      +---- run_validation_epoch
      |          |
      |          +---- model.eval()
      |          +---- no_grad()
      |          +---- validation loss
      |
      +---- scheduler.step()
      +---- checkpoint last/best
      +---- early stopping
```

## Model boundary

The trainer receives an existing `nn.Module`. Device placement is owned by the
trainer. The model itself must not call `.cuda()` or load data. The existing
`EncoderWithEmbeddingHead` remains responsible only for image tensor →
normalized embedding.

## Loss boundary

The trainer does not implement Contrastive Loss. A `train_step` and optional
`valid_step` callable are injected:

```python
loss = step_fn(model, batch)
```

The step must return one finite scalar tensor. This allows Sprint 3 to introduce
the approved distance function and metric-learning loss without rewriting the
S2.5 training infrastructure.

## Checkpoint contract

Each checkpoint contains:

- checkpoint version
- completed epoch
- best validation metric
- model state
- optimizer state
- scheduler state
- training history
- training configuration
- early-stopping state
- Python / NumPy / PyTorch RNG state

Files:

```text
checkpoints/
├── last.pt
├── best.pt
└── logs/
    ├── training_events.jsonl
    └── training_summary.json
```

`last.pt` is the resume checkpoint. `best.pt` is written when the monitored
validation loss improves.

## Reproducibility

`set_seed()` seeds Python, NumPy, and PyTorch. CUDA RNGs are seeded when CUDA is
available. Deterministic PyTorch execution is enabled by default in the
training configuration. This setting can be disabled for performance-oriented
runs when reproducibility is not required.

Exact RNG state is also persisted in checkpoints so a resumed run can continue
from the saved random state rather than only reusing the original integer seed.

## Scheduler policy

The baseline scheduler is `CosineAnnealingLR` with one cycle over the configured
number of epochs. `scheduler_name="none"` is supported for controlled tests and
experiments.

## Early stopping policy

The default monitor is `val_loss` in `min` mode.

```text
patience = 3
min_delta = 0.0
```

An improvement resets the bad-epoch counter. Once patience is exhausted,
training stops after the completed epoch has already been checkpointed.

## Logging policy

Every epoch appends a JSON event containing:

- epoch
- training loss
- validation loss
- learning rate
- sample/batch counts
- epoch duration

A final summary records the completed epoch, best validation loss, early-stopping
status, duration, and checkpoint paths.

## Resume policy

Set `TrainingConfig.resume_from` to a trusted `last.pt` or `best.pt` checkpoint.
The trainer restores model, optimizer, scheduler, early-stopping, history and
RNG state. The next epoch is `checkpoint_epoch + 1`.

A checkpoint whose completed epoch is already greater than or equal to the
configured total epoch count is rejected rather than silently doing no work.

## S2.5 → S2.6/S3 boundary

```text
S2.5
Training infrastructure
        |
        v
S2.6
Baseline training orchestration
        |
        v
S3.x
Distance + metric-learning loss + sampling + embedding evaluation
```

The infrastructure is intentionally generic so later metric-learning choices
can be changed without coupling the optimizer/checkpoint/loop layer to one
loss implementation.

## Git workflow

S2.5 is developed on:

```text
s2.5-training-infrastructure
```

The intended merge path is:

```text
main
  |
  +-- s2.5-training-infrastructure
          |
          +-- implementation commits
          +-- tests
          +-- documentation
          |
          v
       Pull Request
          |
          v
   local full test suite
          |
          v
       merge → main
```

Before opening the PR:

```bash
git fetch origin
git checkout s2.5-training-infrastructure
git pull origin s2.5-training-infrastructure
git checkout main
git pull origin main
git checkout s2.5-training-infrastructure
git merge main
pytest -v
```

If the branch has no conflicts and all tests pass, push the branch and open the
PR. Do not merge an untested training branch directly into `main`.
