# S3.13 — Generalization / Model Selection Gate

## Objective

S3.13 is the final model-selection experiment before the MVP model is treated as the runtime candidate.

The task answers three questions:

1. Does a Siamese model generalize to product groups that were completely unseen during training?
2. Does `s3.5_random` remain the strongest candidate when evaluated under that stricter protocol?
3. If the best model remains weak, is the next action a model/training upgrade rather than a runtime-architecture change?

## Why S3.13 is required

S3.11 evaluates the current metric-learning checkpoints with leave-one-image-out retrieval on the existing train gallery. Those product groups were available during model training, so S3.11 is useful for controlled retrieval comparison but is not a clean unseen-product generalization test.

S3.13 fixes that limitation by creating a new group-disjoint training/evaluation experiment and retraining the candidate models.

## Protocol

```text
Dataset 1 train manifest
        |
        +--> multi-image product groups
        |       |
        |       +--> 80% group-disjoint training groups
        |       |
        |       +--> 20% unseen product groups
        |                |
        |                +--> multiple images/product
        |
        +--> singleton groups remain training-only distractors

Training:
  candidate model sees training groups only
        |
        v
  group-aware pairs
        |
        v
  Siamese training
        |
        v
  candidate checkpoint
        |
        v
  embeddings for the complete Dataset 1 train gallery
        |
        v
  S3.8 product search + S3.9 ranking
        |
        v
  queries restricted to unseen product groups
```

The gallery contains both seen training products and unseen held-out products. This is intentional: a real runtime gallery can contain products whose visual identity was not present in the training set. The ground-truth query product is nevertheless completely absent from the training data.

## Group split

- Only Dataset 1 `train` samples participate in S3.13.
- Product groups with at least two images are eligible for holdout.
- A stratified group split is used with a deterministic seed.
- The default holdout fraction is 20%.
- Singleton product groups remain in the training pool because they cannot support same-product retrieval evaluation.
- No product group may occur in both the training and holdout sets.

The split itself is persisted as `experiments/generalization/s3.13/s3.13_group_split.json`.

## Candidate models

The four existing Sprint 3 candidates are retrained under the same group-disjoint split:

- `s3.4_hybrid`
- `s3.5_random`
- `s3.5_same_category`
- `s3.5_cross_category`

Training hyperparameters remain aligned with the established Siamese training setup unless explicitly overridden by the runner. The experiment changes the data split, not the model architecture.

## Retrieval evaluation

For every image belonging to an unseen held-out product group:

- the query image itself is excluded;
- another image from the same product remains in the gallery;
- the product-level S3.8 search is used;
- S3.9 deterministic ranking is used;
- the query product is the only relevant product identity.

Official comparison metrics:

- Top-1
- Top-5
- Top-10
- MRR

Similarity Score from S3.10 is not used for evaluation.

## Model selection rule

Candidates are ordered lexicographically by:

1. higher Top-1;
2. higher Top-5 when Top-1 ties;
3. higher MRR when Top-1 and Top-5 tie.

This is a **selection rule**, not a universal production-accuracy threshold. S3.13 does not automatically declare a model production-ready merely because it wins the comparison.

Global:

```text

experiments/generalization/s3.13/s3.13_generalization_gate.json
```

Binary checkpoints and embeddings remain local runtime artifacts because the repository ignores `*.pt`/`*.pth`.

## Interpretation

S3.13 separates two decisions:

### Model selection

Which existing candidate generalizes best?

### Model adequacy

Is the absolute unseen-product retrieval performance strong enough for the intended MVP objective?

A candidate can win S3.13 and still justify a future Model V2 investigation. Conversely, if a different existing candidate wins, the runtime model can be switched without redesigning the inference/API/UI architecture.

## Architecture impact

S3.13 is evaluation/training infrastructure only. It does not modify:

- `InferencePipeline`
- `QueryProcessor`
- `GalleryLoader`
- `SimilaritySearchEngine`
- `ProductRanker`
- `SimilarityScoreConverter`
- FastAPI endpoints
- MVP UI

Only the selected model checkpoint changes the runtime model artifact.

Policy identifier: `s3.13-group-disjoint-generalization-v1`.
