# S4.8 — End-to-End Testing

## Purpose

S4.8 validates the complete MVP runtime path with real image files against the running API:

`Image → HTTP /search → QueryProcessor → InferencePipeline → Gallery Search → Ranking → Similarity Score → SearchResponse`

For the UI image cards, each scenario also verifies that the top returned product image can be served through:

`GET /result-image/{product_id}`

## Scenarios

| Test | Scenario | Expected behavior |
|---|---|---|
| 1 | Ring image → similar rings | HTTP 200, non-empty unique results, category `ring` |
| 2 | Necklace image → similar necklaces | HTTP 200, non-empty unique results, category `necklace` |
| 3 | Same ring under a different angle | HTTP 200, non-empty results, category remains `ring` |
| 4 | Same ring under different lighting | HTTP 200, non-empty results, category remains `ring` |
| 5 | Query image whose product is absent from the runtime Gallery | HTTP 200 with nearest Gallery products; no OOD rejection is expected in the current MVP |

## Test data policy

Tests 1 and 2 default to Dataset 1 `test/` images. This keeps the query images outside the S3.7 train Gallery and avoids trivial exact-gallery-image retrieval.

Test 3 and Test 4 accept real manually selected images through CLI arguments. If those arguments are omitted, the runner creates controlled robustness variants from the ring test image. Test 3 now uses a **12-degree BILINEAR rotation with `expand=False`**, matching the geometry/resampling policy used by training augmentation. Test 4 uses reduced brightness and increased contrast.

## Rotation diagnostic and resolution of the original Test 3 failure

The first S4.8 implementation generated the angle variant with **BICUBIC + `expand=True`**. With the known Ring query image `ring_161_jpg.rf.ad1f0fa2a46757f02686ee9abd024646.jpg`, that construction returned `bracelet` and placed the first Ring product at rank 4.

Before changing the model, `EXP-S4.8-ROTATION-DIAGNOSTIC` compared the original transformation with training-like controlled rotations:

| Variant | Result | First Ring rank |
|---|---|---:|
| 0° reference | Ring | 1 |
| +5° BILINEAR, `expand=False` | Ring | 1 |
| +10° BILINEAR, `expand=False` | Ring | 1 |
| +12° BILINEAR, `expand=False` | Ring | 1 |
| −12° BILINEAR, `expand=False` | Ring | 1 |
| +12° BICUBIC, `expand=True` (original S4.8) | Bracelet | 4 |

The controlled experiment provides strong evidence that the original failure was caused by **test construction / transformation geometry**, not by a fundamental rotation-robustness failure in the current Siamese embedding model. In particular, the model correctly handled +12° even though the training rotation range was only approximately ±10°.

Therefore the model was deliberately **not retrained or modified** for this issue. The S4.8 runner was corrected to use the validated transformation.

The full diagnostic report is stored as:

`experiments/e2e/s4.8_rotation_diagnostic.json`

The diagnostic protocol is documented separately in:

`docs/S4.8-Rotation-Diagnostic.md`

## Test 5 and OOD limitation

Test 5 defaults to an image discovered under Dataset 2 and verifies that its file path is absent from the configured runtime gallery metadata. A caller may provide another external image with `--out-of-gallery-image`.

The current retrieval system does not implement an out-of-distribution (OOD) detector or calibrated rejection threshold. Therefore a product that is not present in the Gallery is expected to receive the nearest available Gallery products rather than a `NO_RESULTS` response. Test 5 validates graceful behavior and Gallery-only result identity; it does not claim that the system can prove product absence.

## Execution

Start the real MVP API first with the selected S3.5 random checkpoint:

```bash
python scripts/run_api.py --checkpoint <path-to-siamese-checkpoint>
```

Then, from another terminal:

```bash
python scripts/run_e2e_tests.py
```

The runner automatically discovers the default Dataset 1 ring/necklace test images and a Dataset 2 out-of-gallery image when the expected local dataset paths exist.

For explicit real angle/lighting images:

```bash
python scripts/run_e2e_tests.py \
  --ring-image <ring-test-image> \
  --necklace-image <necklace-test-image> \
  --angle-image <real-angle-image> \
  --light-image <real-lighting-image> \
  --out-of-gallery-image <external-image>
```

The machine-readable report is written to:

`experiments/e2e/s4.8_e2e_report.json`

The report contains scenario status, query paths, returned categories/products/similarity scores, latency, and the out-of-gallery flag.

## Interpretation

S4.8 is a runtime/integration validation, not a replacement for S3.11 quantitative retrieval evaluation. A failed category expectation in Tests 1–4 is a real model/retrieval robustness signal and should be investigated rather than hidden by relaxing the assertion. The rotation investigation demonstrates the required diagnostic procedure: first compare the failing transformation against the training augmentation policy, then change the test only when controlled evidence identifies a construction problem.

## Current acceptance criterion

After the validated Test 3 transformation is used, S4.8 should be re-run end-to-end. The expected acceptance state is **5/5 scenarios passed**. No model retraining is justified by the original rotation failure alone.
